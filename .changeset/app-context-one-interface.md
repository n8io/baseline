Each bounded context has one interface. A context's `index.ts` now exports `<context>ContextCreate({ connections })`, which picks the context's adapters from the connections, traces its Use cases with `telemetryUseCasesTrace` and returns `{ useCases, routes, handlers, schedules, seeds }` (`handlers` and `schedules` only with the queue piece), plus `<context>Schedules` (the Schedules' names and crons, for migrate) and its Published language: input and error types, Domain event schemas, specifications the UI needs, `<aggregate>ErrorStatus` and `<context>Scopes`. Transitions, ports, repositories and `<context>UseCasesCreate` are no longer exported. `adapters/inbound/index.ts` is gone: `index.ts` imports each inbound adapter, and inbound adapters import `domain/`, `application/` types and the files beside `index.ts`, never `index.ts` itself (a cycle). `src/use-cases.ts` exports `contextsCreate(connections)` (was `domainsUseCasesCreate`), which builds each context after the contexts it reads and returns `{ <context>Context, ... }` (type `Contexts`), and `ContextMounts`, the shape the roots mount. `src/server.ts` mounts every context's `routes` and subscribes its `handlers`, `src/worker.ts` starts every context's `handlers` and `schedules`, `seedsRun(mounts: ContextMounts[])` (was `seedsRun(useCases)`) runs every context's `seeds` in build order (a seed gets only the Actor: seeds that pass rows to each other go in one entry, and a context reads another's rows through its upstream), `src/migrate.ts` syncs each `<context>Schedules`, and `uiLoadContextCreate` takes `contexts`. A context that reads another takes its Bridge-built readers as `upstream`, and its `index.ts` exports the reader types its Bridges implement. Architecture rules: A5 lets outside code import only a context's `index.ts`; A1 and A3 fail business code or an inbound adapter that imports its own context's `index.ts` (a cycle, since `index.ts` imports the adapters); A18 fails a context that `contextsCreate` does not both build and return, and a context `index.ts` that leaves `<context>UseCasesCreate(...)` unwrapped. `structure.test.ts` no longer asks for `adapters/inbound/index.ts`. `context-create` and `aggregate-create` write this shape.

To upgrade a Project: after `pnpm template-upgrade`, for each context move what its composition-root lines did into its `index.ts` as `<context>ContextCreate`, following `app@<this version>:apps/app/src/contexts/foo/index.ts`: its routes from `src/server.ts`, its Event handlers from `src/server.ts` and `src/worker.ts`, its Schedules from `src/worker.ts` (and `<context>Schedules` for `src/migrate.ts`), its seeds from `src/seed.ts`, and its Use cases build from `src/use-cases.ts`. Then make `contextsCreate` in `src/use-cases.ts` call each `<context>ContextCreate` in build order, passing a reading context its Bridges as `upstream`, delete each `adapters/inbound/index.ts`, make every file inside a context that imported it or the context's `index.ts` import the `domain/`, `application/` or adapter file itself (outside code keeps importing only `index.ts`), and replace `useCases.<context>UseCases` with `contexts.<context>Context.useCases`. `pnpm check` and `pnpm test` name what is left: A5 for an outside import past `index.ts`, A3 for an adapter importing `index.ts`.
