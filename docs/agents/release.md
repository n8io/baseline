# Walkthrough: ship a change in baseline

Read when someone asks how to get a change to a Package, the Template or `app-ci.yml` released, or asks to be walked through a Release. To start one, ask your agent: "Walk me through shipping this change with docs/agents/release.md."

## How to guide

- Take one step at a time. Say what the step does and why, show the command, and run it only after the person says go.
- After each step, show what changed and how to tell it worked. Stop at the first failure and explain it before you try anything else.
- Ask before anything that cannot be undone: merging the Version packages PR publishes to npmjs, and a published version cannot be reused.
- End by summarising what was released and where Projects pick it up.

## Steps

1. **Branch and change.** Work on a branch; main takes changes only through pull requests. Run the Verify commands in [AGENTS.md](../../AGENTS.md) on what you touched.
2. **Changeset.** A change that should ship needs one: `pnpm exec changeset`, pick each Package it touches, plus `app` for a Template change. Help the person pick patch, minor or major: a change that breaks a Package's exports, or a Template change Projects must adapt to, is major. When an upgrade note asks a Project to copy code, point at that file in the release (`app@<version>:apps/app/<path>`) instead of pasting a different snippet: a copy identical to the Template's merges cleanly in `pnpm template-upgrade`. Dependency update PRs carry none, so they never release.
3. **Pull request and CI.** `ci.yml` runs `packages` (check, test and build on what changed), `sast`, `integration` (the Template with Foo) and `render`. A pull request that changes only Markdown outside `apps/app` skips `integration`, `render`, `render-and-test` and `api-only`, which then report skipped, and that satisfies their required checks. In `packages`, a Package's README or CHANGELOG is no input of its build or tests; the root tests read the repository's docs, so they still run. `render` builds a real Project, the previous release upgraded to this change with `template-upgrade` plus two new Domains, and `render-and-test` runs the whole `app-ci.yml` on it. A step in `packages` and one in `check` only warn on glossary aliases. Check: every required check is green.
4. **Merge.** Squash only, no approval needed once green. `ci.yml` runs again on main, which saves the Turborepo cache later pull requests restore. A Dependabot auto-merge pushes with `GITHUB_TOKEN`, which starts no run, so `ci.yml`'s `main-run` job dispatches that run on main instead. Check: that run is green.
5. **Version packages PR.** `release.yml` runs on main and opens or updates "🔖 Version packages" with the new versions and changelogs. It pushes as the GitHub App `n8io-baseline-release` (Contents and Pull requests, installed on this repository only), with a token minted from the repository variable `RELEASE_APP_CLIENT_ID` and the secret `RELEASE_APP_PRIVATE_KEY`, so the PR gets a normal `pull_request` run of `ci.yml` that the main ruleset counts. A `GITHUB_TOKEN` push would start none. Check: every required check on that PR is green; if the token step fails, the App's variable, secret or installation is missing. Show the person the version bumps before merging.
6. **Release.** Merging the Version packages PR publishes each changed Package to npmjs by trusted publishing with provenance, and tags `app@x.y.z` when the Template changed. Check: `git ls-remote origin 'refs/tags/app@*'` lists the tag, and `https://registry.npmjs.org/@n8io/baseline-<name>/<version>` answers (it can lag a few minutes).
7. **`v<major>` moves.** The same `release.yml` run, with no changesets left, points the `v<major>` tag at the newest `app@<major>.x.y`. Projects whose `ci.yml` calls `app-ci.yml@v<major>` run the new CI from then on, and take the new Template with `pnpm template-upgrade`. A check that could fail a Project that passed before, or an added, renamed or removed job (a required check), never goes into the current `v<major>`; it ships as the next one. A Template major also starts a new `v<major>`, even when `app-ci.yml` is unchanged. The Version packages PR already points the Template's `ci.yml` at the new major: `pnpm run version` runs `scripts/ci-pin-write.ts`, and `test/ci-pin.test.ts` fails if the pin and the Template's major differ. Check: `git ls-remote origin refs/tags/v<major>` answers; until it does, a Project made from the new release cannot start its CI, so re-run `release.yml` if the step failed.
