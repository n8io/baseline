Prototype · Baseline template architecture

What a domain looks like on disk

Reopened to choose between two ways to arrange the app's folders: each domain holds its own layers (domain-first), or each layer holds every domain (layer-first). Both are judged against the template's goals, in priority order: Obvious > Enforced > Swappable > Short.

Everything below the open question was settled earlier and holds either way. Throwaway page; only the decision moves forward.

Decided Domain-first

Domain-first or layer-first?

Domain-first: domains/foo/ holds every layer Recommended

apps/app/src/
├─ server.ts                       # composition root for the HTTP process
├─ worker.ts                       # composition root for the worker process
└─ domains/
   └─ foo/
      ├─ index.ts                  # fooDomainCreate(ports); the only import from outside
      ├─ foo-errors.ts
      ├─ ports.ts                  # FooRepository, FooEventPublisher, FooPorts
      ├─ models/foo.ts
      ├─ rules/foo-name-unique.ts  (+ .test.ts)
      ├─ use-cases/foo-create.ts   (+ .test.ts), foo-get, -list, -update, -delete
      ├─ api/                      # every way a request arrives
      │  ├─ foo-routes.ts          # HTTP
      │  ├─ foo-consumer.ts        # messages from the bus or queue
      │  ├─ foo-schedule.ts        # timer calls a use case
      │  └─ foo-socket.ts          # real-time push
      └─ spi/
         ├─ foo-table.ts
         ├─ foo-repository.postgres.ts
         ├─ foo-repository.memory.ts
         └─ foo-event-publisher.memory.ts

Add one operation, fooArchive

domains/foo/
├─ rules/foo-archivable.ts       + test
├─ use-cases/foo-archive.ts      + test
├─ api/foo-routes.ts             one new route
├─ ports.ts                    one new repository method
└─ spi/foo-repository.*.ts      implement it
→ 1 folder open. Every file to copy sits next to its neighbour.

Add a new domain, bar

cp -r domains/foo domains/bar   # or a generator; rename foo → bar
→ 1 folder. A domain missing spi/ is visible next to foo/ in one listing.

Against the goals

How each layout scores

GoalDomain-firstLayer-first
1 · ObviousOne folder per domain. An agent working on foo opens domains/foo/ and every file it copies is a sibling. ls domains/ lists the business areas.ls src/ shows the hexagon at once. But one operation spans three trees, and the agent must know to look in all three.
2 · EnforcedOne rule table keyed on the folder name. One public entry per domain (index.ts), checked by one rule. A structure test compares each domain to a fixed list of folders.Same layer rules. No single public entry. A missing spi/bar/ needs a cross-layer structure check.
3 · SwappableA domain can move to its own service as one folder; its imports already stop at the folder edge.Splitting a domain out means collecting three folders and building a boundary that did not exist.
4 · ShortImports stay inside one folder: ../models/foo.ts.Imports cross trees: ../../core/foo/models/foo.ts. One index.ts per layer per domain.
New scopeConsumers, schedules and sockets are more files in api/; the publisher is another port and adapter. Nothing new at the top level.Same files, spread across api/foo/ and spi/foo/.
Glossarydomains/foo/ is exactly one Domain.Needs core/ and a new glossary term, because a top-level domain/ would hold only part of a Domain.

The strongest case for layer-first: changes that touch one layer everywhere (rate limits on every route, spans on every adapter) stay in one folder, and the two most-starred clean-architecture templates use it. Here those changes live in shared packages and Hono middleware instead, and those templates each hold one service, which is one of our Domains.

Settled earlier · holds either way

Inside a domain

  • Business logic (models/, rules/, use-cases/, ports.ts, foo-errors.ts) has no business with api/ or spi/. Rules import only models and do no I/O.
  • api/ holds every inbound adapter and calls use cases, never spi/. spi/ implements ports and imports only ports.ts and models/. Neither holds business rules.
  • A factory per use case: fooCreate = (ports: FooPorts) => async (input) => …, bound once in fooDomainCreate. Routes see use cases, never ports. No container.
  • No domain imports another domain.
Settled earlier · naming

Naming across two domains

Example: a document is signed, then the signer is notified. Entity first, then the business verb. Each use case is named for what its own domain does, never for the whole chain.

ThingNameFile
Use casedocumentSigndocument/use-cases/document-sign.ts
Its inputDocumentSignInputdocument/models/document.ts
RuledocumentSignabledocument/rules/document-signable.ts
ErrorDocumentAlreadySignedErrordocument/document-errors.ts
Event it publishesDocumentSigneddocument/models/document.ts
Use case, other domainnotificationSendnotification/use-cases/notification-send.ts
Consumer linking themnotificationConsumernotification/api/notification-consumer.ts
  • No compound names: documentSign, not documentSignAndNotify. Reactions belong to the domains that react.
  • Business verbs from the glossary, not CRUD verbs: documentSign, not documentUpdate.
  • A child entity goes between entity and verb: documentSignerAdd.
  • Events are past tense, entity first, no suffix: DocumentSigned is a model. Only errors and ports keep suffixes.
  • The receiving use case stays generic. The consumer maps DocumentSigned to NotificationSendInput. Never notificationOnDocumentSigned.
How a request moves

POST /foo, start to finish

Shown domain-first. Error mapping and the database adapter's shape are drafts; separate tickets decide them.

  1. apps/app/src/server.ts · composition root

    Startup wires adapters to the domain

    const db = createDatabase(config.DATABASE_URL); // adapter picked from URL scheme
const foo = fooDomainCreate({
  fooRepository: db.kind === "postgres"
    ? fooRepositoryPostgres(db)
    : fooRepositoryMemory(),
});
app.route("/foo", foo.routes);
  2. domains/foo/api/foo-routes.ts

    The route validates input and calls one use case

    export const fooRoutes = (u: FooUseCases) =>
  new OpenAPIHono().openapi(fooCreateRoute, async (c) => {
    const foo = await u.fooCreate(c.req.valid("json"));
    return c.json(foo, 201);
  });
  3. domains/foo/use-cases/foo-create.ts

    The use case applies the rules and calls a port

    export const fooCreate =
  ({ fooRepository }: FooPorts) =>
  async (input: FooCreateInput): Promise<Foo> => {
    const data = FooCreateInput.parse(input);
    return fooRepository.insert({ ...data, id: crypto.randomUUID() });
  };
  4. domains/foo/ports.ts

    The port says what the domain needs, not how

    export interface FooRepository {
  insert(foo: Foo): Promise<Foo>;
  findById(id: FooId): Promise<Foo | undefined>;
  list(query: FooQuery): Promise<Foo[]>;
  update(id: FooId, patch: FooUpdateInput): Promise<Foo | undefined>;
  remove(id: FooId): Promise<boolean>;
}
export type FooPorts = { fooRepository: FooRepository };
  5. domains/foo/spi/foo-repository.postgres.ts

    The adapter does the real work

    export const fooRepositoryPostgres = (db: PostgresDatabase): FooRepository => ({
  insert: async (w) => (await db.insert(fooTable).values(w).returning())[0],
  ...
});
Decision

Domain-first, chosen on 2026-10-31. Layer-first stays on this page for the record.
