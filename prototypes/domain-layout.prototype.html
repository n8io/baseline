What a domain looks like on disk

An example widgets domain, sketched three ways. Pick a folder layout and a way for use cases to get their ports. The marked option is my recommendation. Everything here is throwaway; only the decision moves forward.

Terms follow the glossary: a domain is one entity and its operations, a port is an interface the domain declares, the SPI is the adapters that implement ports. The route layer has no glossary term yet; it is called http/ below.

Decided

The layout we picked

Layout A, flattened: business logic sits at the domain's root. Routes moved to api/, because requests may arrive over HTTP, a message bus or gRPC. Use cases get their ports from a factory. The API and the SPI hold no business rules.

apps/app/src/domains/widgets/
├─ index.ts                    # createWidgetsDomain(ports); the only import from outside
├─ widget.ts                   # Widget entity: Zod schemas + types
├─ widget-errors.ts
├─ ports.ts                    # WidgetRepository, WidgetPorts
├─ use-cases/                  # all business rules live here and in the root files
│  ├─ create-widget.ts         # createWidget = (ports) => async (input) => ...
│  ├─ create-widget.test.ts
│  └─ get-, list-, update-, delete-widget.ts
├─ api/                        # inbound: HTTP routes today; may add consumers, gRPC
│  ├─ routes.ts
│  └─ routes.test.ts
└─ spi/                        # outbound adapters that implement ports
   ├─ widgets-table.ts
   ├─ widget-repository.postgres.ts
   └─ widget-repository.memory.ts
  • Root files and use-cases/ import nothing from api/ or spi/.
  • api/ imports the root files and use-cases/, never spi/. spi/ imports only the root files (ports.ts, entity types).
  • Nothing outside the domain imports past index.ts. No domain imports another domain.

The options below are kept for the record.

Decision 1

Folder layout

A · Folders by layer Recommended

apps/app/src/domains/widgets/
├─ index.ts                    # the only import other code may use
├─ core/                       # no imports from spi/ or http/
│  ├─ widget.ts                # Widget entity: Zod schemas + types
│  ├─ widget-errors.ts         # WidgetNotFoundError, ...
│  ├─ ports.ts                 # WidgetRepository (port)
│  └─ use-cases/
│     ├─ create-widget.ts
│     ├─ create-widget.test.ts # runs against the memory adapter
│     ├─ get-widget.ts
│     ├─ list-widgets.ts
│     ├─ update-widget.ts
│     └─ delete-widget.ts
├─ spi/                        # may import core/ports, never use-cases
│  ├─ widgets-table.ts         # Drizzle table
│  ├─ widget-repository.postgres.ts
│  ├─ widget-repository.postgres.test.ts  # Testcontainers
│  └─ widget-repository.memory.ts
└─ http/                       # may import core, never spi/
   ├─ routes.ts                # @hono/zod-openapi route definitions
   └─ routes.test.ts
  • Each folder is one layer, so the dependency-cruiser rules are three lines: core imports nothing outside itself; spi and http import core; nothing outside the domain reaches past index.ts.
  • An agent adding an operation copies one file in use-cases/ and one route. The place is obvious.
  • Cost: one operation touches two folders.

B · Folders by use case

apps/app/src/domains/widgets/
├─ index.ts
├─ widget.ts
├─ widget-errors.ts
├─ ports.ts
├─ create-widget/
│  ├─ create-widget.ts         # use case
│  ├─ create-widget.route.ts   # its route
│  └─ create-widget.test.ts
├─ get-widget/ ...
├─ list-widgets/ ...
├─ update-widget/ ...
├─ delete-widget/ ...
└─ spi/
   ├─ widgets-table.ts
   ├─ widget-repository.postgres.ts
   └─ widget-repository.memory.ts
  • One operation lives in one folder, so adding one is a single copy.
  • Layer rules depend on file suffixes (*.route.ts may not import spi/), which are easier to get wrong.
  • For a CRUD-sized domain, five near-identical folders is a lot of nesting for five functions.

C · Flat files with suffixes

apps/app/src/domains/widgets/
├─ index.ts
├─ widget.entity.ts
├─ widget.errors.ts
├─ widget.ports.ts
├─ widget.use-cases.ts         # all five operations
├─ widget.use-cases.test.ts
├─ widget.routes.ts
├─ widget.repository.postgres.ts
├─ widget.repository.memory.ts
└─ widget.table.ts
  • Fewest files; reads well while the domain is small.
  • One use-cases file grows without limit as real business rules arrive, and agents tend to keep appending to it.
  • Layer rules depend on suffixes, the same weakness as B.
Decision 2

How a use case gets its ports

A · A factory per use case, bound once per domain Recommended

// core/use-cases/create-widget.ts
import type { WidgetPorts } from "../ports.ts";
import { NewWidget, type Widget } from "../widget.ts";

export const createWidget =
  ({ widgets }: WidgetPorts) =>
  async (input: NewWidget): Promise<Widget> => {
    const data = NewWidget.parse(input);
    return widgets.insert({ ...data, id: crypto.randomUUID() });
  };

// index.ts
export const createWidgetsDomain = (ports: WidgetPorts) => {
  const useCases = {
    createWidget: createWidget(ports),
    getWidget: getWidget(ports),
    listWidgets: listWidgets(ports),
    updateWidget: updateWidget(ports),
    deleteWidget: deleteWidget(ports),
  };
  return { useCases, routes: widgetRoutes(useCases) };
};

// a test
const { createWidget } = createWidgetsDomain({ widgets: memoryWidgetRepository() }).useCases;
  • Plain functions and closures. No library, nothing for an agent to learn.
  • Routes call useCases.createWidget(body) and never see a port.
  • Wiring happens in one place per domain, so it is obvious where a new port gets passed in.

B · Ports as the first argument on every call

// core/use-cases/create-widget.ts
export const createWidget = async (
  { widgets }: WidgetPorts,
  input: NewWidget,
): Promise<Widget> => { ... };

// http/routes.ts
app.openapi(createRoute, async (c) => {
  const widget = await createWidget(c.var.ports, c.req.valid("json"));
  return c.json(widget, 201);
});
  • The simplest possible function shape.
  • Every route needs the ports, so they ride on Hono's context. That puts adapters in the http layer's reach and weakens the boundary rule.

C · A dependency-injection container (Awilix or similar)

container.register({
  widgets: asFunction(postgresWidgetRepository).singleton(),
  createWidget: asFunction(createWidget),
});
const createWidget = container.resolve("createWidget");
  • Scales to many dependencies and scoped lifetimes.
  • Wiring is resolved by name at runtime, so a missing port fails at startup instead of in the type checker.
  • Adds a library and a concept agents have to understand. More than a CRUD domain needs.
How a request moves

POST /widgets, start to finish

Shown with layout A and factory A. Error mapping and the database adapter's shape are drafts; separate tickets decide them.

  1. apps/app/src/server.ts · composition root

    Startup wires adapters to the domain

    const db = createDatabase(config.DATABASE_URL); // adapter picked from URL scheme
const widgets = createWidgetsDomain({
  widgets: db.kind === "postgres"
    ? postgresWidgetRepository(db)
    : memoryWidgetRepository(),
});
app.route("/widgets", widgets.routes);
  2. widgets/http/routes.ts

    The route validates input and calls one use case

    export const widgetRoutes = (u: WidgetUseCases) =>
  new OpenAPIHono().openapi(createWidgetRoute, async (c) => {
    const widget = await u.createWidget(c.req.valid("json"));
    return c.json(widget, 201);
  });
  3. widgets/core/use-cases/create-widget.ts

    The use case applies the business rules and calls a port

    const data = NewWidget.parse(input);
return widgets.insert({ ...data, id: crypto.randomUUID() });
  4. widgets/core/ports.ts

    The port says what the domain needs, not how

    export interface WidgetRepository {
  insert(widget: Widget): Promise<Widget>;
  findById(id: WidgetId): Promise<Widget | undefined>;
  list(query: WidgetQuery): Promise<Widget[]>;
  update(id: WidgetId, patch: WidgetPatch): Promise<Widget | undefined>;
  remove(id: WidgetId): Promise<boolean>;
}
export type WidgetPorts = { widgets: WidgetRepository };
  5. widgets/spi/widget-repository.postgres.ts

    The adapter does the real work

    export const postgresWidgetRepository = (db: PostgresDatabase): WidgetRepository => ({
  insert: async (w) => (await db.insert(widgetsTable).values(w).returning())[0],
  ...
});
